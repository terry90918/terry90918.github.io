這篇文章帶你從一個 bug 修復任務，看懂 Cursor pstack 的提示詞如何合作。讀完後，你應該能說明每一層負責什麼，也能替自己的 AI Agent 工作流程畫出第一版架構。

範例依據 pstack 0.15.24 的原始碼 commit [1e5c90a](https://github.com/cursor/plugins/tree/1e5c90a4b6f249917bd21fe361b3a2a7deb741b8/pstack)。Cursor 的產品功能會更新；本文將 pstack 的固定版本分析和 Cursor 現行文件分開標示。

## 先看任務如何流過 pstack

把 pstack 想成一套工作流程。使用者描述目標，`/poteto-mode` 選擇工作流程，playbook 排定步驟；每個步驟再按需要載入技能和原則。只有需要委派時，主代理才使用角色提示詞安排子代理。最後由主代理對照真實執行結果和完成條件。

![pstack 任務路徑圖：入口路由到 playbook，再使用技能、原則和委派提示，最後以真實證據驗證；Benny 位於獨立的自動化路徑](/images/cursor-pstack/pstack-task-flow.svg)

圖中的主線不是每個任務都要走完的固定管線。`/poteto-mode` 選一份 playbook；playbook 只呼叫適用的技能。原則在相關決策點提供短規則。需要子代理時，角色提示詞會把任務範圍、限制和回報格式交代清楚。主代理仍要檢查回報，再用實際程式或介面驗證結果。

Benny 走另一條路。它是一套複製到專案後才設定的 Slack 自動化素材，不是一般對話中用 `/名稱` 呼叫的技能。它的設定提示與自動化提示範本會引導外部事件流程；一般程式任務不會經過這條路。[Benny 設定說明](https://github.com/cursor/plugins/blob/1e5c90a4b6f249917bd21fe361b3a2a7deb741b8/pstack/automations/benny/README.md)

### 每一層回答不同的問題

| 層         | 它回答的問題                               | pstack 的例子                                                   |
| ---------- | ------------------------------------------ | --------------------------------------------------------------- |
| 路由器     | 這是什麼任務？該走哪份流程？               | `/poteto-mode` 判斷 Investigation、Bug fix、Feature 等路徑      |
| Playbook   | 工作先後順序是什麼？每一步要留下什麼證據？ | `bug-fix.md` 規定重現、定位根因、修正和重跑                     |
| Skill      | 某一種工作要怎麼做？                       | `how` 解釋程式機制，`tdd` 處理便宜且明確的回歸測試              |
| Principle  | 遇到特定取捨時，該採用什麼判斷規則？       | `fix-root-causes` 要求修根因，`prove-it-works` 要求檢查真實產物 |
| 角色提示詞 | 委派時，子代理要處理什麼、回報什麼？       | `poteto-agent` 與調查、設計、審查用的 prompt template           |
| 工具和權限 | Agent 實際能做什麼？哪些動作需要批准？     | Cursor 工具、MCP 外部服務連接器、專案指令和執行權限             |
| 證據和交付 | 怎樣才算完成？要向誰交付什麼？             | 原始 bug 在相同介面消失，然後回報根因、修正和驗證結果           |

Cursor 將技能定義為可版本控制的工作知識與流程。技能可由 Agent 判斷是否適用，也可在前台用 `/` 呼叫；設定 `disable-model-invocation: true` 後，只會在明確呼叫時載入。[Cursor Agent Skills 文件](https://cursor.com/docs/skills)

pstack 選擇較明確的路由方式。固定版本中的 54 份 `SKILL.md` 有 53 份設了 `disable-model-invocation: true`，由 `/poteto-mode` 選好流程後再載入所需技能。[pstack 的 `/poteto-mode`](https://github.com/cursor/plugins/blob/1e5c90a4b6f249917bd21fe361b3a2a7deb741b8/pstack/skills/poteto-mode/SKILL.md) 這讓入口和執行細節分開，也增加路由器維護負擔。完整數量和例外見[提示詞逐項解析](/posts/2026/cursor-pstack-prompt-analysis)。

提示詞只描述 Agent 應採取的步驟。它不會自行提供工具、檔案權限或外部服務存取。Cursor 會另外依 Run Mode、沙箱和批准設定處理工具呼叫。[Cursor Run Modes 文件](https://cursor.com/docs/agent/security/run-modes)

## 用一個日期 bug 走完整流程

以下是教學用的假設情境，不是 pstack 專案中的真實 bug。假設使用者回報：

> 報表匯出時選擇 2026-10-15，下載檔案卻顯示 2026-10-14。請修好，並用相同的匯出流程確認日期正確。

在 Cursor 中，使用者可以從明確入口交代任務：

```text
/poteto-mode 修復報表日期 bug：在 Asia/Taipei 選擇 2026-10-15 後匯出，檔案裡卻是 2026-10-14。先在相同介面重現，再確認根因，修好後重跑這個匯出流程。
```

### 1. 路由器判斷使用者要修 bug

使用者要求修正已發生的錯誤，所以 `/poteto-mode` 選 Bug fix。若使用者只問日期為什麼改變，路徑會是 Investigation；若要求新增匯出格式，則會是 Feature。路由依預期結果決定，不依「日期」「匯出」這些關鍵字硬分流。

**這一步的產物：** Bug fix playbook，而不是尚未經過調查的程式修改方案。

### 2. 在原本的介面重現，建立可觀察基線

Bug fix playbook 要求主代理先用對應的 control skill 操作實際介面。輸入相同日期和時區，重新匯出檔案，記下輸入值、輸出值和重現步驟。若一開始沒有重現成功，不能把「找到可疑程式碼」當成 bug 已確認。

**這一步的產物：** 一份可重跑的失敗情境，例如輸入 `2026-10-15`，匯出結果是 `2026-10-14`。

### 3. 用證據排除假設，直到機制明確

`how` 用來追日期從介面到匯出檔案的資料路徑。若需要了解近期改動或回歸背景，再用 `why` 查歷史。接著提出幾個假設，例如日期解析、時區換算或匯出格式化，並用程式執行時的資料逐一排除。

假設觀察結果顯示，程式用本地年月日建立本地午夜的 JavaScript `Date`，再呼叫 `toISOString().slice(0, 10)`。台北時間的 2026-10-15 午夜換成 UTC 後是 2026-10-14 16:00，因此再切出 UTC 日期就會少一天。這時才有證據支持根因：程式把「日曆日期」當成「時間點」轉換。

`fix-root-causes` 會影響修正方向：刪除或繞過時區轉換，比在匯出結果加一天更能修正資料模型問題。若實際執行證據不支持這個假設，就不能照這個例子寫修正。

**這一步的產物：** 已由執行證據支持的根因，而非猜測或 Agent 的自述。

### 4. 選最小修正，再決定是否需要設計或測試技能

若修正跨越函式邊界，Bug fix playbook 先叫 `architect` 畫清楚資料形狀和介面。若修改集中在單一日期欄位，保留日期字串而不轉成時間點可能已足夠，不必額外設計一套抽象。

如果能用便宜、穩定的測試捕捉錯誤，`tdd` 會先加入失敗測試，再做修正。若測試需要昂貴的整合環境或不可靠的 mock，就使用最接近真實路徑的檢查。Bug fix playbook 要求委派調查和修正。主代理仍負責重現、確認根因、審查差異和重跑原始情境。每份角色提示詞都要包含檔案範圍、已確認的根因、禁止擴大的範圍和要求回傳的證據。Cursor 子代理有自己的上下文，也能設定工具權限和唯讀狀態；實際能力仍受宿主設定限制。[Cursor Subagents 文件](https://cursor.com/docs/subagents)

**這一步的產物：** 一個根因對應一個修正，以及能證明這個修正的測試或檢查。

### 5. 由主代理審查，再跑原始情境

主代理檢查委派結果和 diff，執行聚焦驗證，再透過原來的匯出介面重跑 2026-10-15。測試可以證明日期格式分支的結果，但不能單獨證明使用者看到的匯出 bug 消失。`prove-it-works` 把最後判斷帶回實際產物。

Bug fix playbook 要求失敗重現和修正分開留在 Git 歷程中，也要求原始重現最後通過。若相同介面無法操作，就回報受阻原因，不能把測試通過寫成「bug 已修好」。完成回報說明壞在哪裡、根因、修正，以及原始情境如何驗證。[Bug fix playbook 原文](https://github.com/cursor/plugins/blob/1e5c90a4b6f249917bd21fe361b3a2a7deb741b8/pstack/skills/poteto-mode/playbooks/bug-fix.md)

**這一步的產物：** 匯出流程現在仍收到 `2026-10-15`，並附上可檢查的測試或重現結果。

這個流程也說明各層不該互相取代。Playbook 排順序，Skill 提供可重用方法，Principle 改變決策，角色提示詞界定委派工作，工具產生執行證據，主代理負責審查與交付。

## 從零設計一套自己的工作流程

不要先寫一份包含所有規則的長 prompt。先從團隊反覆遇到的工作和可觀察結果開始，再決定哪些內容值得成為獨立檔案。

### 1. 先列出常見任務和完成證據

收集真實任務，例如解釋程式、修 bug、加功能、重構、調查效能。每個任務都寫兩件事：使用者要的結果，以及外部怎麼確認結果。

| 使用者想完成的事 | 合適的完成證據                       |
| ---------------- | ------------------------------------ |
| 了解匯出流程     | 原始碼路徑、資料流和引用位置         |
| 修好日期少一天   | 相同匯出介面重跑後顯示正確日期       |
| 新增 CSV 匯出    | 使用者入口可下載符合規格的 CSV       |
| 重構日期處理     | 原有行為測試和實際流程都維持相同結果 |

證據若說不清楚，先把任務定義補完整。單寫「品質要好」或「修好」不足以讓 Agent 判斷何時停止。

### 2. 寫一個小路由器

路由器只回答「使用者要什麼結果」和「該走哪份流程」。至少要能分清只讀調查、已有缺陷、新功能、純重構和效能調查。也要寫明無法判斷時該怎麼做，例如提出一個必要問題，或回報目前不確定。

不要把每一個操作步驟、測試指令或程式慣例塞進路由器。那些內容屬於 playbook、技能或專案規則。入口越長，越難看出它該選哪條路。

這是一份起點，不是完整規格：

```markdown
依使用者要求的結果選一條流程：

- 只想了解現有行為或原因：Investigation
- 報告已發生的錯誤並要求修復：Bug fix
- 要新增或改變產品行為：Feature
- 明確要求結構改動且行為不變：Refactoring

依目標結果分類，不依單一關鍵字分類。若目標無法判斷，只問能決定路由的必要問題。
```

讀一段使用者請求時，先找「要了解、要修好、要新增，還是只改結構」。這個選擇比路由器裡列更多關鍵字可靠。

### 3. 把每種長流程寫成 playbook

Playbook 描述有順序和停止條件的工作。先從 Bug fix 寫一份，因為「先重現、再找根因、修後重跑」能清楚示範 gate 的作用。

每個階段都指定動作、輸入、輸出證據和停止條件。遇到沒有權限、找不到測試介面、證據互相矛盾時，寫明要如何回報。這些例外比「自行想辦法」更能防止流程悄悄降低標準。

可以先用這份骨架：

```markdown
# 流程名稱

## 何時使用

說明哪種使用者目標會選到這份流程。

## 需要的輸入

列出流程所需的資訊和工具。

## 步驟

每一步寫明要做什麼，以及必須留下什麼證據。

## 何時停止

說明能力不足、證據衝突或動作不安全時如何處理。

## 完成條件

指出哪個可觀察結果能證明任務完成。

## 回報內容

列出 Agent 要交付給使用者的資訊。
```

### 4. 把可重用操作和決策規則分開

一段規則若跨多份流程反覆使用，而且有明確觸發情境，就考慮寫成 principle。例如「修 bug 時先找根因」會影響多個除錯步驟。若內容是一串可重複操作，例如「沿著 API 呼叫追到資料庫」，就寫成 Skill。

一個簡單判斷方式是問：

- 這段內容規定「何時選哪種做法」嗎？把它放進 Principle。
- 這段內容規定「怎麼完成一類工作」嗎？把它放進 Skill。
- 這段內容規定「多個步驟按什麼次序完成」嗎？把它放進 Playbook。
- 這段內容只適用於某個特定子代理嗎？把它放進角色提示詞。

同一條規則不要在多個地方各寫一份。若同一指示要重複第二次，先決定哪個檔案是權威來源，再從其他地方連結過去。

### 5. 只為有明確價值的工作建立子代理

子代理適合長時間探索、可平行的工作線或需要獨立審查的任務。單一步驟、範圍小且主代理很快能驗證的工作，直接完成通常更省成本。

子代理提示詞至少要說清楚任務、背景、可修改範圍、不可做的事、回報格式和需要附上的證據。`readonly` 等工具能力也要設在 Cursor 能執行的設定中；文字要求只能說明預期，不能取代權限設定。

### 6. 把安全邊界交給工具和設定

凡是會讀取專案外資料、呼叫外部服務、刪除內容或發出訊息，都要檢查宿主工具是否真的提供能力，以及當前權限是否允許。提示詞可要求 Agent 先確認或取得批准，但不能用 prompt 文字代替工具限制、沙箱或權限政策。[Cursor Run Modes 文件](https://cursor.com/docs/agent/security/run-modes)

### 7. 用真實任務測試路由和停止條件

拿近期的真實任務當測試材料，逐題檢查：

1. 路由器有沒有選對 playbook？
2. 每個 playbook 有沒有取得指定證據？
3. 工具不足或證據矛盾時，流程會不會停下來？
4. 子代理的回報是否能由主代理檢查？
5. 完成條件是否能由實際程式、介面或外部狀態驗證？

測試一個成功案例還不夠。也要加入「無法重現」「權限不足」「CI 通過但畫面仍錯」這類失敗情境。它們能檢查你的架構是否知道何時不能宣稱完成。

## 用三個問題檢查你的設計

先自己回答這三題，再往下看參考答案。

1. 使用者問「匯出檔案為什麼少一天」，要走哪條流程？
2. 使用者說「匯出日期少一天，請修好」，要走哪條流程？
3. bug 已重現，使用者要求新增另一種匯出格式，要走哪條流程？

### 參考答案與證據

1. **Investigation。** 先找日期從畫面到匯出檔的程式路徑。完成時交付可核對的資料流和來源位置。
2. **Bug fix。** 先在相同介面重現輸入和錯誤輸出。完成時在相同介面重跑，確認原始問題消失。
3. **Feature。** 先確認新格式的輸入、輸出和使用方式。完成時從使用者入口產生符合規格的檔案。

只知道路由名稱，還不算理解這套設計。每一題都要能指出第一份證據、完成證據和證據不足時的停止條件。

能用自己的專案完成這三步，代表你已掌握架構的核心：把使用者意圖轉成工作流程，把反覆使用的方法拆成技能，讓原則影響重要判斷，再用工具和證據檢查結果。接著才需要讀完整份 pstack 索引，了解它的每個提示如何實作這些選擇。

## 動手設計第一版

挑一種你每週都會遇到的工作，先只做一條流程：

1. 從最近的任務中挑五個例子，寫下每個任務的預期結果。
2. 建立一個只有幾條路徑的路由表，並標出還不能判斷的情況。
3. 選一條最常用的路徑，依照上面的骨架寫 playbook。
4. 把跨流程重複出現的判斷規則提成 Principle，把可重複操作提成 Skill。
5. 用一個成功案例和一個受阻案例試跑，檢查 Agent 有沒有選對路，以及有沒有在證據不足時停下來。

先讓一條流程能穩定產生可檢查的結果，再增加新路由或子代理。這樣你可以從實際失敗調整設計，不必先維護整套 pstack 的規模。
